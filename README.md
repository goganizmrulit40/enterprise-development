# Лабораторная работа №2 - Сервер (REST API)

## Цель работы

Реализовать серверное приложение на ASP.NET Core (REST API), предоставляющее базовые CRUD-операции для сущностей автосервиса, а также API для выполнения аналитических запросов из ЛР1. Хранение данных на данном этапе осуществляется в памяти.

## Архитектура проекта

Для соблюдения принципов чистой архитектуры (Clean Architecture) проект разделен на слои:

- `AutoService.Domain` — доменные модели и интерфейсы репозиториев.
- `AutoService.Contracts` — DTO (Data Transfer Objects) и интерфейсы сервисов.
- `AutoService.Application` — бизнес-логика (сервисы, маппинг, аналитика).
- `AutoService.Infrastructure` — реализация репозиториев (работа со списками в памяти).
- `AutoService.Api` — контроллеры и конфигурация внедрения зависимостей (DI).
- `AutoService.AppHost` — проект оркестратора .NET Aspire для запуска API.

## Реализованный функционал

**1. CRUD-операции:**
Реализованы контроллеры для управления всеми основными сущностями:
- `CarsController` (автомобили)
- `ClientsController` (клиенты)
- `MechanicsController` (механики)
- `OrdersController` (заказы)
- `WorksController` (виды работ)

Для каждой сущности доступны методы `GET`, `POST`, `PUT` и `DELETE`. Взаимодействие происходит через DTO. Для методов обновления используются отдельные DTO без поля `Id`.

**2. Аналитические запросы:**
Логика 5 запросов из первой лабораторной вынесена в `ReportsController` и доступна по HTTP:
1. Получение механиков, специализирующихся на выбранном виде работ.
2. Получение клиентов, чьи автомобили обслуживались у указанного механика, с сортировкой по ФИО.
3. Получение клиентов с повторными обращениями за последний месяц.
4. Подсчёт суммарной стоимости работ для выбранного заказа.
5. Получение пяти наиболее частых видов работ.

**3. Обработка исключений:**
Для аккуратной обработки ошибок добавлен глобальный `ExceptionHandlingMiddleware`. Он перехватывает непредвиденные исключения, логирует их и возвращает клиенту статус 500 (Internal Server Error). Ожидаемые ситуации (например, 404 Not Found при отсутствии сущности) обрабатываются в контроллерах.

## Интерфейс приложения (Swagger)

Для удобства тестирования и документирования эндпоинтов подключен Swagger UI. Настроено отображение XML-комментариев (`summary`) из кода. При запуске проекта браузер автоматически открывается на странице Swagger.
На странице представлены все реализованные контроллеры (CRUD для сущностей и аналитические запросы).

## Тестирование

Для тестирования используется **xUnit v3**.
Реализовано 7 тестов:
- 5 юнит-тестов на LINQ (из ЛР1).
- 2 интеграционных теста (`ApiIntegrationTests`), которые запускают оркестратор **.NET Aspire** (`AutoService.AppHost`) и проверяют ответы HTTP-эндпоинтов.

С помощью команды
```commandline
dotnet test
```
получим результат выполнения:
```
Сводка тестового запуска: Пройден!
  итог: 7
  сбой: 0
  успешно: 7
  пропущено: 0
  длительность: 12s 782ms
```
Длительность тестового запуска объясняется запуском Aspire.

## Запуск
1. Восстановить зависимости: `dotnet restore`
2. Запустить сервер: `dotnet run --project AutoService.Api`
3. Открыть в браузере документацию Swagger по адресу: `http://localhost:5199/swagger`.

Запуск также осуществляется через IDE: необходимо запустить проект AutoService.Api, и браузер со страницей Swagger UI откроется автоматически.
